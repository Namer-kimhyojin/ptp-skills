# PTP 반짝 웹툰 · 산업 한 컷 일일 발행

산업 이슈를 계기로 일반 독자가 용어 한 개를 쉽게 이해하도록 돕는 웹툰이다. `workflow=creative`, `content_category=spark-webtoon`, `content_mode=educational-comic`으로 구분한다. 기존 유머 단편과 별도 운영한다. 테오·피오와 두 캐릭터의 실루엣·상징·이름은 제외한다. 사물극, 익명의 일반인·실무자 역할, 쉬운 비유와 간단한 도식을 소재에 맞게 사용한다. 등록 캐릭터를 쓰지 않는 단발 등장인물도 콘티·제작 기록에 명시하고 실제 생성 자산과 권리를 검수한다. `character-set none`은 이 스킬의 인물 없는 사물극 조건에 맞을 때 사용한다.

## 발행일의 이슈와 주제

1. 실제 KST 발행일을 기준으로 포항TP 공식 사업공고·사업소개·성과자료·장비 안내 또는 정부·지자체 공식 자료를 열어 포항TP가 직접 수행하거나 기업·이용자를 지원하는 사업이나 서비스를 먼저 찾는다. 사업명과 포항TP의 구체적인 역할이 확인되고 그 활동이 웹툰의 핵심 개념과 직접 이어지는 후보만 남긴다. 포항에 있다는 점, 산업 분야가 같다는 점, 조직도에 담당팀이 있다는 점, 다른 기관이 운영한다는 자료만으로는 선정하지 않는다. 포항TP의 역할을 설명의 마지막에 붙여야만 관련성이 생기는 주제도 제외한다. [포항TP 소식](https://www.ptp.or.kr/main/board/index.do?manage_idx=11&menu_idx=266)
2. 공식 근거를 확보한 후보에 한해 최근 3일의 산업 이슈를 우선 비교한다. 후보별 실제 사건일, 최초 발표일, 달라진 점, 일반 독자가 배울 개념과 포항TP 활동의 접점을 적는다. 사건의 직접 발표와 개념을 설명하는 별도의 1차 자료를 각각 열어 확인한다. 적합한 후보가 부족하면 최근 14일 이내로 넓히고 이유를 적는다. 직접 연결성을 입증할 후보가 없으면 확인한 자료와 후보별 제외 사유를 실행 기록에 남기고 당일 주제 확정·제작·게시를 보류한다.
3. 과거 일일 예약·제작·게시 주제를 모두 읽고 기존 길찾기 편성의 교육 주제와 SNS 공개·예약·임시저장도 확인한다. 후보의 핵심 정의와 독자가 얻을 답을 비교한다. 동일 사건의 기사 바꿔쓰기, 제목 변경, 동의어로 바꾼 동일 개념은 제외한다. 같은 산업의 다른 개념은 설명이 어떻게 다른지 기록한다. 당일 보류는 중복을 피하기 위해 다음 날에 몰아 올리지 않는다.
4. 선택한 브리프에 `source_key/publish_date/title/sector/concept_key/issue_key/aliases/reader_question/plain_definition/issue_summary/why_now/similarity_review/page_count/page_count_reason/mascots`를 기록한다. `concept_key`와 `issue_key`는 안정된 영어 소문자·숫자·하이픈 식별자다. `aliases`에는 같은 개념을 가리키는 국내외 표기만 넣는다. `mascots=excluded`를 적용한다. `sources`의 항목은 `url/title/publisher/role/supports/checked_date`를 포함한다. `role`은 `issue-primary/definition-primary/ptp-primary/corroboration` 중 하나다. 교체용 공식 서비스 소개의 `service-primary`는 아래 교체 절차를 따른다. `issue-primary`에는 원래 사건·공표의 `event_date`도 쓴다. 3일을 넘긴 후보는 `extended_window_reason`에 이유를 넣는다. 후보 비교, 사실과 해석, 과거 유사 후보의 제외 이유를 브리프에 함께 보존한다.
5. `ptp_connection`에 `status=verified`, `role=operator`(직접 수행) 또는 `role=supporter`(직접 지원), `program`(공식 사업·서비스명), `direct_relevance`(같은 활동이 핵심 개념을 어떻게 설명하는지), `team`, `support`, `story_link`, `page`, `source_urls`를 기록한다. `official_evidence`에 `url`, `locator`(페이지의 절·표·항목명), `excerpt`(사업과 수행·지원 역할을 입증하는 실제 문구)를 넣는다. URL은 `sources`의 `ptp-primary`와 `ptp_connection.source_urls` 양쪽에 둔다. 정부·지자체 자료에서 근거를 가져올 때는 포항TP가 해당 활동의 수행·지원 주체로 명시된 문구를 확인한다. 공식 사이트 도메인과 증거 필드 검사에 더해 실제 문구가 이번 주제의 사업과 역할을 입증하는지 읽어 확인한다. `check-topic`을 통과한 브리프만 예약·제작에 사용한다.

## 재단 사업·시설·성과를 보여 주는 마지막 장

기획할 때 독자가 무엇을 이해하고 어떤 포항TP 지원·시설·성과를 확인하면 좋을지 먼저 정한다. 포항TP의 실제 역할을 본편 사례에 연결하고 마지막 한 장에는 회차와 관련된 공식 명칭, 재단이 한 일이나 제공하는 것, 독자가 그것을 어디에서 확인할지를 독립적으로 읽히게 배치한다. 개념 설명에 다섯 장이 필요하면 안내 장을 한 장 더 제작한다. 5장 안에서 설명과 안내가 모두 명확하면 마지막 장에 통합해도 된다.

- 시설 편은 공식 시설명, 실제 이용 가능한 공간·서비스, 시설소개·이용안내·입주 안내의 확인 경로를 제시한다. 예를 들어 기업 사무실과 공동 회의실 편은 포항지식산업센터의 입주공간·회의실 시설현황으로 연결한다. 입주 안내와 신청은 구분하고, 특정 모집의 신청을 안내하려면 게시 직전 공고 번호, 공고 원문과 접수 기한, 공식 접수 경로를 확인한다. 상시 교육형 반짝웹툰에서 최신 공고 신청 유도를 제외하도록 위임된 경우에는 시설·사업 안내를 사용한다.
- 성과 편은 공식 결과 발표나 보고서에 나온 실제 성과를 기준일·대상·단위와 함께 전달한다. 확인하기 어려운 수치나 효과는 생략하고 근거가 있는 지원 내용이나 실제 운영 사례를 안내한다. 예정된 사업이나 지원 기준을 완료 실적으로 표현하지 않는다.
- 마지막 장의 확인 경로는 공식 페이지 제목과 홈페이지 메뉴, 검증된 URL 또는 QR 중 독자가 사용할 수 있는 수단으로 넣는다. 이미지의 짧은 안내를 캡션의 출처·경로로 보완한다. 기사·공고 제목만 적고 독자가 어디를 찾아야 하는지 빠뜨리지 않는다.

브리프나 검수 spec에 `ptp_outcome_page`로 장 번호, 전달 목적, 재단 역할, 공개 근거와 확인일, 최종 이미지에서 읽히는 메뉴 경로 또는 URL, 확인 행동을 기록한다. 공고 신청을 넣은 경우 적용한 공고·기간 검증 근거도 연결한다. 마지막 장을 360px에서 읽어 사업·시설 이름과 확인 경로를 찾을 수 있는지 채널별 제출 전에 확인한다.

## 제작과 검수

### 매회 다른 시각 연출

최근 완성·발행한 반짝웹툰 최대 6편의 실제 이미지와 제작 기록을 살펴 화풍, 색채, 재료감, 등장 방식, 카메라와 컷 구성, 도입·결말을 비교한다. 이번 주제에 맞는 서로 다른 시각 방향을 2~3개 구상하고, 가장 최근 작품과 확연히 다른 하나를 선택한 이유를 기록한다. 예를 들면 손그림 잉크, 수채화, 종이 콜라주, 레트로 만화, 픽셀 아트, 점토 모형 등에서 자유롭게 고르고 필요하면 다른 화풍을 새로 제안한다. 예시를 순서대로 돌리는 고정 템플릿으로 쓰지 않는다.

동일 회차 안에서는 읽기 흐름과 등장 대상의 정체성을 유지하면서 장면마다 시점, 거리, 행동, 표정과 화면 구도를 바꾼다. 연속된 컷에서 같은 그림이나 포즈에 말풍선만 바꾸지 않는다. 글자와 그림을 함께 생성하고, 매 장의 한국어 문구·말풍선과 360px 가독성은 최종 이미지로 검수한다. `quality-spec.json`의 `creative.signature`, 최근 작품 비교와 `difference_evidence`에는 실제 선택한 화풍·색채·구도와 차이를 구체적으로 남긴다. 주제에 맞는 연출과 내용 전달을 우선하며 확인되지 않은 타인의 고유 화풍을 모방하지 않는다.

검증된 포항TP 사업이나 서비스에서 독자가 궁금해할 상황을 골라 표지의 질문과 실제 사례를 만든다. 예를 들어 공식 장비 안내에서 포항TP의 화장품 소재 분석 지원을 확인했다면, 두 시제품의 차이를 어떻게 비교할지 묻고 포항TP가 지원하는 분석을 사례로 설명한다. `story_link`와 `page`에 실제 장면과 최종 이미지 번호를 기록하고, 채널별 게시 직전에 공식 근거와 직접 연결성을 다시 대조한다. 사업의 지원 사례와 현재 모집 여부를 구분하며 과거 공고에는 신청을 유도하지 않는다.

최소 **완성 게시 이미지 5장**이다. 장마다 질문, 쉬운 뜻, 생활 속 사례, 비교나 흔한 오해, 정리·적용 중 하나를 맡긴다. 6장 이상이 필요하면 사례나 절차를 나누고 장수의 이유를 기록한다. 채널에서 지원하는 장수와 실제 미리보기를 확인한다. 핵심 의미는 이미지에서도 이해할 수 있게 하고 약어는 쉬운 말로 먼저 푼다. 실제 360px 미리보기에서 한 문장 설명과 다른 상황에 적용하는 질문에 답할 수 있어야 한다. 투자 판단과 의료·안전 조언은 제외한다. 사업·시설·검증된 성과와 공식 확인 경로는 위 마지막 장 기준에 따라 안내한다.

`quality-spec.json`에는 [콘텐츠 검수](content-review.md)의 `education_review` 구조를 쓰고 `industry_topic_sha256`, `forbidden_mascots_absent=true`, 실제 `mascot_exclusion_evidence`를 추가한다. 첫 장은 `question`, 마지막은 `apply`이며 가운데 최소 한 장씩 `explain`과 `example`을 둔다. 포항TP의 실제 지원 사례를 통해 개념을 지역에 적용하는 결말도 `apply`에 해당한다. 연결 사례가 있는 장은 사실 검수 근거에 담당 조직·공식 자료·그림에 표현한 지원 행동을 기록한다. 최종 이미지의 글자, 독해 순서, 오해 소지, 출처 표기와 테오·피오 제외를 실제로 확인하고 해시를 연결한다. 출처는 캡션 또는 마지막 장에 달며, QR을 쓰면 원본과 축소본의 실제 해독 결과를 확인한다.

## 운영과 복구

현재 정책은 작업 폴더의 `outputs/PTP_SPARK_INDUSTRY_WEBTOON_PLAN/일일_운영정책.json`이다. 매일 11:30 한국시간에 당일 조사·제작을 시작하고, 실제 검수를 마친 채널부터 공개한다. 편성 날짜 밖이나 11:30 전에는 새 제출을 진행하지 않는다. 시계가 몇 분 빨라 `wait`가 나오면 당일 `planned_at`까지 기다린다. 같은 날에는 재개를 포함해 새 기획 한 건만 예약한다. 기존 격일 웹툰과 공고는 각각의 편성을 따르며 Meta 계정 조작은 `foundation-meta` 점유를 공유한다. 다른 작업이 점유 중이면 그 작업에 간섭하지 않고 당일 15분 간격으로 최대 4회 재확인한다.

```powershell
$policy = 'outputs/PTP_SPARK_INDUSTRY_WEBTOON_PLAN/일일_운영정책.json'
python scripts/spark_runtime.py select --policy $policy
python scripts/spark_runtime.py check-topic --policy $policy --brief <검토한_기획_JSON>
python scripts/spark_runtime.py begin --policy $policy --triggered-at <실제_호출_ISO_시각>
python scripts/spark_runtime.py reserve --policy $policy --run-id <run_ID> --brief <검토한_기획_JSON>
```

스킬 설치 경로의 스크립트를 호출한다. 당일 키는 `ptp:spark:industry-daily-YYYY:epMMDD`다. `reserve`가 저장한 파일과 SHA를 작업 근거로 쓴다. 예약된 당일 주제, 등록된 제작 ID와 완성 파일, 원래 제출 시도를 재사용한다. 준비를 끝낸 manifest에는 `runtime_contract_version=1`, 게시 순서의 `final_image_paths`, `runtime.plan_path`(일일 정책 절대 경로), `runtime.scope=foundation-meta`, `runtime.topic_sha256`를 둔다. 예약 기획 JSON의 원본 사본을 manifest.files에 같은 해시로 넣고, 검수 spec에도 같은 해시를 연결한다.

편성 밖 날짜의 수동 발행을 사용자가 명시한 경우에만 정책의 `manual_dates`에 해당 KST 날짜와 요청 근거를 추가하고 `begin --context interactive`로 실행한다. 수동 실행 날짜도 자동 실행과 같은 키·중복·검수 조건을 적용한다.

[공통 자동 실행](automated-operation.md)의 실제 계정 preflight, ready 단계, 채널별 미리보기 JSON을 사용한다. 기존 게시·예약·초안을 확인하고 아래 공통 게이트로 당일 출처·주제 예약·실행 점유·계정·이미지 해시·순서를 검증한다.

```powershell
python scripts/series_runtime.py gate --source-key <키> --platform <채널> --manifest <manifest> --preview <채널_미리보기> --report <새_게이트_JSON>
python scripts/social_runtime.py stage --run-id <run_ID> --stage submission --evidence <새_게이트_JSON>
python scripts/publication_history.py record --source-key <키> --platform <채널> --account <계정> --manifest <manifest> --status submitting --series-gate <새_게이트_JSON> --evidence <실제_근거>
```

게시 버튼을 누르기 전에 채널별 제출 시도를 등록한다. 성공 채널은 보존하며 `submitting/unknown`이면 원래 시도와 공개 화면을 먼저 대조한다. 두 계정에 올릴 때 실제 공개 주소, 시각, 이미지 순서, 캡션·대체텍스트, AI 표기, 사용한 경우 플랫폼 이미지 QR을 회차의 별도 `publication-results.json`과 게시 장부에 남긴다. 게시 시간은 UI에서 확인한 실제 시각을 적는다. 공고 우선 점유나 브라우저·검수 차단은 단계와 이유를 남긴 뒤 안전하게 종료하고, 보유한 실행은 실제 근거를 기록해 반환한다.

사용자가 당일 공개한 회차의 교체를 요청하면 대화형 실행으로 원래 회차 키를 재사용한다. 원래 주제 파일을 보존하고 `daily-topics/YYYY-MM-DD.correction.json`에 교체 사유와 공식 근거를 기록한다. 공식 서비스 소개로 교체할 때는 `service-primary`와 별도 `definition-primary` 자료를 각각 연결한다. 수정 manifest의 `runtime.replaces_topic_sha256`는 원래 주제 파일, `runtime.topic_sha256`는 수정 주제 파일을 가리킨다. 수정 패키지와 채널별 미리보기를 먼저 검수한 뒤, [기존 게시물 교체](social-publishing.md)의 삭제 근거와 채널별 `gate --replacement` 및 `--replacement-evidence`로 원래 시도와 새 시도를 연결한다.
