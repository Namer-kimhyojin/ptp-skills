# SNS 자동 로그인·세션 재사용

예약 실행과 브라우저 자체의 미제공·`queued` 복구는 [자동 실행·편성·복구](automated-operation.md)를 함께 적용한다. 이 문서의 인증 확인과 무인 실행 환경의 접근 가능성은 별도 결과로 기록한다.

게시 단계 또는 로그인 설정 요청에서만 읽는다. 목표는 같은 브라우저에서 인증을 재사용하여 반복 입력을 줄이는 것이다. 사용자가 지정한 내장 브라우저(`iab`)를 우선하며, 다른 브라우저의 세션을 가져오거나 사용자 지정과 다르게 전환하지 않는다.

## 설정과 확인 범위

- `config/social-accounts.json.authentication`은 브라우저 선택·저장 로그인 사용 여부·사용자의 저장 요청 근거만 담는다. 실제 비밀번호, 인증코드, 쿠키, 세션 토큰은 이 파일·job·보고서·채팅에 저장하지 않는다.
- 비밀번호 저장을 명시적으로 요청받았으면 지정한 브라우저가 제공하는 저장 UI/공식 보안 입력 기능으로 설정한다. 지원 기능이 없으면 저장 완료로 표시하지 않는다. 자체 평문 파일, 브라우저 DB 추출, 쿠키 복사, 코드 내 하드코딩으로 대신하지 않는다.
- 페이지 핸들 `pohangtpoffcial`은 Facebook 로그인 ID가 아니다. 페이지 관리자의 로그인 계정과 게시 대상을 구분한다. `account_id`를 로그인 폼에 자동 입력하지 않는다. 로그인 계정이 여럿이고 재단 관리자 계정을 식별할 근거가 없으면 사용자에게 브라우저에서 선택하도록 요청한다.
- 최초 로그인 정보가 없으면 사용자가 공식 로그인 화면에 한 번 직접 입력하도록 한다. 기존 비밀번호를 채팅으로 요구하지 않는다. 내장 브라우저의 비밀번호 저장 기능과 Meta의 '로그인 정보 저장'·로그인 세션 유지는 서로 다른 기능이며 각각 실제 동작을 확인한다.

## 실행 절차

1. 현재 제공되는 브라우저 API·기능을 확인하고 지정된 브라우저에서 `https://business.facebook.com/`을 연다. 로그인된 관리 화면이면 로그아웃하지 말고 5단계로 간다. 이전 실행의 `published_verified`는 과거 근거이며 현재 로그인 확인을 대신하지 않는다.
2. 로그인 화면이면 공식 Meta 화면의 Facebook/Instagram 로그인 경로를 이용한다. Meta 팝업이 열리지 않으면 보이는 공식 Facebook 링크로 이동해 같은 브라우저에서 인증한 뒤 Business Suite로 돌아온다. 로그인 URL은 `https`와 정확한 호스트를 확인한다. `facebook.com`, `www.facebook.com`, `business.facebook.com`, `instagram.com`, `www.instagram.com` 밖의 인증 경로는 확인 없이 비밀정보를 전달하지 않는다.
3. 사이트가 제공하는 저장 프로필 클릭 로그인 또는 브라우저의 저장 계정·자동 완성을 사용한다. `authentication.facebook_login_profile_url`과 실제 저장 프로필을 대조하되 표시 이름만으로 확정하지 않는다. 비밀번호 표시·추출·복사 없이 화면상 해당 계정을 확인하여 프로필/로그인 버튼을 한 번 누른다. 폼이 비어 있고 저장 로그인이 없으면 사용자 직접 입력으로 인계한다. 로그인이 계속 실패하면 같은 비밀번호를 반복 제출하지 않는다.
4. 로그인 정보 저장 UI가 나타나고 해당 서비스·브라우저 저장에 대한 사용자 요청이 있으면 저장을 선택한다. 추가 권한·계정 연결·보안 설정 변경은 일반 로그인과 별도로 다룬다. 2단계 인증, CAPTCHA, 기기 잠금 해제, 비밀번호 변경·복구, 보안 경고는 사용자에게 해당 화면을 인계하고 보호 기능을 끄지 않는다. 필요시 `markHandoff()`로 로그인 탭을 보존한다.
5. 인증 후 재단 Facebook 페이지와 연결된 Instagram의 실제 식별자·프로필 URL, 콘텐츠 작성 기능을 재확인한다. 공개 프로필이 보인다는 이유만으로 로그인·작성 권한이 있다고 판단하지 않는다. 다른 페이지로 로그인됐으면 원래 재단 대상을 확인하기 전 게시하지 않는다.
6. 새 작업이면 원본 최신성과 중복 이력을 다시 확인하여 게시 단계를 계속한다. **게시 제출 후** 인증이 풀렸다면 원래 `attempt_id`와 패키지 manifest를 보존하고 콘텐츠·예약 목록에서 원래 시도를 먼저 찾는다. `submitting/unknown`을 로그인 실패 때문에 `failed`로 바꾸거나 재제출하지 않는다.

내장 브라우저에서 두 계정이 Business Suite에 연결되어 있으면 별도 Instagram 로그인이 불필요할 수 있다. 화면에서 연결과 작성 권한을 확인한 경우에만 그렇게 기록한다.

## 상태와 재개

실행별 `work/.../authentication-status.json`에는 비밀정보 없이 다음을 기록한다. 실사용 설치 설정은 관측한 상태만 갱신한다.

| 필드 | 의미 |
|---|---|
| `browser` | 실제 사용 브라우저: `iab`, `edge` 등 |
| `session_status` | `unchecked`, `login_required`, `challenge_required`, `authenticated`, `target_verified` |
| `credential_storage_status` | `not_checked`, `not_exposed`, `available_unconfigured`, `saved_verified` |
| `site_saved_login_status` | `not_checked`, `offered`, `enabled_ui_accepted`, `relogin_verified`: 사이트의 저장 프로필 로그인과 브라우저 비밀번호 금고를 구분 |
| `login_method` | `existing_session`, `saved_login`, `user_sign_in` 또는 `null` |
| `checked_at`, `evidence` | 확인 시각과 비밀정보 없는 UI 관찰 |
| `resume_stage`, `attempt_ids` | 재개 단계와 제출 후 조정이 필요한 기존 시도 ID |

`saved_verified`는 브라우저 비밀번호 저장 UI의 성공 근거가 있을 때만 쓴다. Facebook의 `비밀번호 저장` 안내에서 프로필 클릭 로그인을 설정한 경우에는 `site_saved_login_status=enabled_ui_accepted`로 기록한다. `authenticated`와 브라우저 비밀번호 저장 완료, 앱 재시작 후 세션 유지, 무인 재로그인 성공을 구분한다. 로그인 화면을 방문한 것만으로 세 가지를 모두 검증했다고 쓰지 않는다.

최초 입력 또는 보안 인증이 필요할 때는 준비된 작업을 보존하고 **어느 브라우저의 어느 화면에서 무엇을 완료하면 이어지는지**만 짧게 안내한다. 답변이 없다는 이유로 인증을 완료 처리하지 않는다. 사용자 인증 후에는 현재 화면을 다시 확인하고 중단 단계부터 이어간다.

## 확인된 환경과 검증

2026-10-22 이 환경의 내장 브라우저에는 비밀번호 금고 API가 노출되지 않았다. 사용자의 최초 직접 로그인 후 같은 내장 브라우저의 새 Facebook 탭에서 로그인 세션 재사용을 확인했고, Facebook의 `비밀번호 저장` 안내(`다음번에 ... 비밀번호를 입력하는 대신 프로필 사진을 클릭`)에서 `확인`을 눌러 사이트의 저장 프로필 로그인을 활성화했다. Business Suite에서 재단 페이지와 연결된 `pohangtp_official`도 확인했다. 이는 브라우저 비밀번호 금고에 원문을 저장했다는 뜻이 아니며 로그아웃 후 재로그인·앱 재시작은 시험하지 않았다. 다음 실행은 현재 상태를 다시 확인한다.

스킬 수정 검증 때문에 실제 계정을 로그아웃하거나 비밀번호를 바꾸거나 게시물을 새로 올리지 않는다. 설정·절차 검증, 기존 세션 확인, 저장 자격증명을 사용한 신규 로그인 검증을 결과에서 구분한다.
