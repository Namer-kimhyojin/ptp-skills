# 재단 SNS 계정 설정·게시·재개

예약 실행은 [자동 실행·편성·복구](automated-operation.md)의 편성 조회·계정 작업 점유·최신 preflight를 먼저 적용한다. 새 계약의 패키지는 기존 기간·제작 장부 검사에 더해 최종 검수 파일과 실제 게시 시각을 장부 제출 시 재확인한다. 기존 성공·불명 시도는 업그레이드로 초기화하지 않는다.

## 계정과 실행 수단

배포본의 `config/social-accounts.json`은 재단의 공개 계정 식별자를 제공한다. 첫 사용 때 직원 본인에게 부여된 Meta 게시 권한으로 로그인하고, 실제 접속 화면의 프로필·페이지 ID 및 작성 권한을 대조한다. `verified_at`, `verified_by`에 실제 근거를 남긴다. 설정을 새로 작성해야 할 때는 `assets/social-accounts.example.json`을 사용한다. 비밀번호·쿠키·토큰·인증코드는 공식 로그인 화면에서만 다룬다.

1. 현재 사용 가능한 SNS 연결 도구의 계정 조회·미디어 업로드·게시·상태 조회 기능을 탐색한다. 제공되면 그 도구를 우선한다. 이미지 제작 도구나 일반 브라우저를 SNS API가 연결됐다고 기록하지 않는다.
2. 사용자가 내장 브라우저 등 특정 수단을 지정했으면 그 수단을 우선한다. 전용 게시 도구가 없거나 브라우저가 지정됐으면 [자동 로그인·세션 재사용](social-authentication.md)을 따라 [Meta Business Suite](https://business.facebook.com/)에 접속한다. 해당 브라우저 사용 지침을 먼저 읽고, 재단 페이지와 연결된 Instagram이 선택 가능한지 확인한다.
3. 두 계정이 연결되지 않았어도 각각 접근 가능한 공식 게시 화면에서 채널별로 진행할 수 있다. 연결 변경·권한 추가는 게시와 다른 변경이므로 사용자 요청 범위를 확인한다. 임의 API 호출이나 미설정 토큰으로 게시 가능하다고 가정하지 않는다.
4. 로그인 화면에서는 지원되는 저장 계정·자동 완성으로 일반 로그인을 진행한다. 저장 정보가 없거나 2단계 인증·기기 확인이 필요하면 준비된 카드·문안·작업 상태를 보존하고 해당 단계만 사용자에게 인계한다. 비밀번호나 인증코드를 채팅에 요구하지 않는다. 게시 기능·파일 업로드가 없는 도구라면 패키지를 완성해 전달하고 필요한 단계를 정확히 알린다.

Meta의 화면·계정별 기능은 바뀔 수 있다. 아래 명칭은 찾아갈 위치의 예시다. 매 실행에서 실제 표시된 버튼·대상을 확인한다. 권한 종류는 [Meta 공식 페이지 접근 권한 안내](https://www.facebook.com/help/289207354498410/)를 참고하고, 업로드 크기는 선택한 도구 화면 및 [Instagram 사진 해상도 안내](https://help.instagram.com/1631821640426723)를 확인한다. API 경로를 쓰면 현재 공식 API 문서의 해당 로그인 방식·필수 권한·미디어 조건을 별도로 확인한다.

## 게시 요청의 범위

- 최종 홍보물의 기본 선택은 검수 뒤 양쪽 채널에 공개하는 것이다. [게시 기본값](default-publication.md)대로 초기 캐릭터 선택에 게시 범위를 묶고, 범위가 확정되면 같은 승인을 반복하지 않는다. 사용자 요청·선택·위임 근거를 `job.json`의 `publication`에 기록한다.
- “초안 저장”은 공개 게시가 아니다. “예약”은 사용자 지정 시각과 `Asia/Seoul`을 확인해 수행한다. 시간 지정이 없으면 임의 예약하지 않는다.
- 광고·부스팅·유료 집행·메시지 발송·프로필 링크 변경은 일반 게시에 포함하지 않는다.

## 중복 방지와 실행 이력

먼저 [제작 이력·기간 관리](notice-tracking.md)를 적용한다. 기존 제작물은 재사용하고 실제 접수기간 안에서만 새 게시를 제출한다. `source_notice.eligibility_path`의 원문 확인 근거와 제작 완료 패키지를 준비한다. 두 계정에 이미 게시한 공고는 새 게시 대상이 아니다.

### 실제 SNS 대조

로컬 장부의 `allowed=true`·`게시 기록 없음`은 이 스킬이 아는 이력만 뜻한다. 새 제작 후보를 확정하기 전에, 또 중단된 게시를 재개할 때, 확인된 Instagram 계정과 Facebook 페이지의 **게시됨·예약됨·초안**을 각각 대조한다. 하나의 통합 화면에서 두 계정이 모두 보이면 함께 확인할 수 있지만 결과는 채널별로 남긴다. 이미 확인된 같은 실행의 근거는 재사용하고, 게시 직전에는 그 이후 추가된 게시·예약·초안만 확인한다.

1. 선택 계정 ID, 콘텐츠 상태, 날짜 필터를 먼저 읽는다. Meta 화면이 최근 90일 등 기본 범위로 열리면 그대로 전체 이력으로 해석하지 않는다. 게시됨은 후보의 **등록일을 포함하거나 그보다 앞선 날부터 현재까지** 조회하고, 예약됨은 미래 예약도 포함하도록 전체 범위 또는 필요한 미래 범위를 확인한다. 초안은 가능하면 전체 기간을 확인한다. 화면이 사용하는 날짜가 게시일·예약일·수정일 중 무엇인지도 기록한다.
2. 검색어는 공고 ID, 사업의 핵심명, 사업연도와 핵심명 조합을 각각 사용한다. ID가 캡션에 없을 수 있으므로 ID 검색만으로 끝내지 않는다. 제목의 괄호·공백·줄임말이 달라질 수 있어 핵심어 검색도 확인한다. 날짜 필터를 바꾼 뒤 검색이 초기화됐는지 확인한다.
3. 목록의 로딩 완료와 적용된 필터를 확인하고 필요한 페이지·더 보기를 끝까지 읽는다. 비어 보이는 화면, 로딩, 오류, 권한 제한, 조회 기간 밖, 일부 페이지만 확인한 상태는 `uncertain`이다. 실제로 검색이 끝난 빈 결과만 `not_found_in_scope`로 기록하며, 이를 모든 과거에 게시한 적 없다는 뜻으로 확대하지 않는다.
4. 비슷한 제목이 나오면 카드·캡션·상세 공고 URL/ID·사업연도를 열어 같은 공고인지 판단한다. 다른 연도나 별도 모집차수는 제목만으로 중복 처리하지 않는다. 발견한 실제 게시 URL/ID 또는 예약·초안 항목 식별자를 보존한다.

작업 폴더의 `remote-duplicate-check.json`에 [기록 예시](../assets/remote-duplicate-check.example.json)를 채운다. 계정·상태별 검색어, 적용 날짜 범위, 확인 시각, 결과, 일치 항목, 화면/API 근거와 한계를 남긴다. 비밀번호·쿠키·토큰은 기록하지 않는다. 이 파일은 실행자의 관찰 기록이며 도구가 원격 부재를 자동 증명한 결과가 아니다. 새 검증 도구나 추가 승인 절차를 요구하지 않는다.

같은 공고의 게시·예약을 발견하면 기존 URL을 연결해 해당 채널의 새 제출을 제외한다. 장부에 없는 과거 결과는 실제 확인 근거로 이관하되, 로컬 카드 파일까지 없는 상황을 `제작 완료`로 꾸미지 않는다. 같은 공고의 초안은 기존 내용을 열어 이어 쓸 수 있는지 확인하며 중복 초안을 만들지 않는다. 초안을 게시 완료·실패로 기록하지 않는다. 한 채널만 완료면 다른 채널만 처리하고, 다음 공고 선택은 [후보 재선정 규칙](notice-tracking.md#원격-대조-후-후보-재선정)을 따른다.

모든 채팅이 같은 `<skill-root>/state/publication-history.jsonl`을 사용한다. 새 실행마다 빈 장부를 만들어 중복 검사를 우회하지 않는다. 이 파일과 `config/social-accounts.json`은 스킬 업데이트 때 보존한다. 예시 템플릿을 실사용 설정 위에 덮어쓰지 않는다.

중복 키는 `source_key=ptp:15:<board_idx>` + `platform` + 정규화한 계정 ID다. 표시 이름 대신 확인된 고정 ID 또는 프로필 URL을 사용하고 다음 실행에서도 같은 값을 유지한다. 소스·문안이 바뀌어도 같은 공고가 이미 게시됐다는 기록은 유지한다.

스크립트는 URL의 www·끝 슬래시·대소문자와 핸들 표기 차이를 정규화한다. 그러나 숫자 ID와 사용자명 사이의 관계는 추정하지 않는다. 기존에 핸들로 기록했다면 뒤에 숫자 ID를 알아도 먼저 기존 기록과 같은 계정임을 대조하고 일관된 키를 유지한다.

```powershell
python scripts/publication_history.py check --ledger state/publication-history.jsonl --source-key ptp:15:8190 --platform instagram --account <확인된계정ID> --manifest <패키지manifest경로>
python scripts/publication_history.py record --ledger state/publication-history.jsonl --source-key ptp:15:8190 --platform instagram --account <확인된계정ID> --manifest <패키지manifest경로> --eligibility <최신접수기간근거.json> --status submitting
```

실제 인자는 `--help`를 확인한다. `<...>`는 실행 전 실제 값으로 바꾼다. 8190은 설명용 예시이며 매 실행 최신 공고 ID로 바꾼다. `submitting` 기록이 성공한 후 반환된 `attempt_id`를 보관하고 해당 채널의 게시 버튼을 누른다. 두 채널을 한 번에 제출할 때도 두 개의 `submitting` 기록을 먼저 성공시킨다.

새 PTP 제출은 기간 근거가 없거나 오래됐거나, 기간 밖이거나, 등록된 제작 완료 패키지와 실제 파일이 맞지 않으면 차단된다. 기본 제작 장부를 다른 빈 파일로 대체하지 않는다. `--content-ledger`는 격리 시험·명시적 이관 전용이다. 기존 시도의 원격 성공을 뒤늦게 확정하는 것은 새 게시가 아니므로 같은 `attempt_id`로 기록을 마무리한다. 최초 실게시를 `published` 이관 명령으로 대신하지 않는다.

- `published`·`scheduled`: 새 게시를 차단하고 기존 URL을 제시한다. 수정·재게시가 요청되면 기존 글을 확인하고 별도 변경 범위를 다룬다.
- `submitting`·`unknown`: 게시 여부가 불명확하다. 새 게시 버튼을 누르지 말고 해당 계정의 콘텐츠 목록·최근 게시물·예약 목록에서 원래 시도를 찾아 조정한다.
- `failed`: 실제 미게시가 확인된 실패만 기록한다. 타임아웃·응답 소실·화면 중단은 `unknown`이다.

`submitting`·`unknown` 시도는 같은 `attempt_id`의 확인 결과를 `record`로 추가해 조정한다. 성공에는 원격 URL 또는 게시물 ID, 확인 근거와 시각을 남긴다. 예약에는 예약 시각을 남긴다. 게시 이력 스크립트는 로컬 기록과 중복 검사 도구이며 외부 게시 성공을 자체 검증하지 않는다. 화면/API 응답에서 확인하지 않은 성공 근거를 입력하지 않는다.

`published`·`scheduled`를 기록한 종료 이벤트는 덮어쓰지 않는다. 게시물 ID로 완료를 먼저 기록한 뒤 공개 URL을 확인했다면 작업 패키지의 `publication-results.json`에 `source_key`, 채널·계정, 기존 `attempt_id`·게시물 ID, 확인한 URL·시각·근거를 연결한다. URL 보충을 위해 종료 시도에 다시 `record`하거나 새 시도를 만들지 않는다. `Terminal history cannot be overwritten`은 이 보호 규칙이며 별도 결과 문서로 보완한다.

## Meta Business Suite 화면에서 등록

선택한 [단일 이미지 모드](single-image-social.md)는 각 게시물에 최종 PNG **1개만** 업로드한다. 카드뉴스는 확정한 다중 장 순서를 적용한다. 미리보기·원화·문자 검수용 이미지를 게시 사진에 추가하지 않는다. 형식이 달라도 공고·계정별 중복 키와 기간·상태 검사는 동일하다.

1. 재단 페이지를 선택하고 **콘텐츠/게시물 만들기**에 해당하는 작성 화면을 연다. **게시 대상**에서 확인된 페이스북 페이지와 인스타그램 프로필만 선택한다. 개인 프로필·다른 기관 페이지가 섞이지 않았는지 확인한다.
2. 카드 PNG를 01부터 순서대로 업로드한다. 영상은 [영상 게시 확인](video-production.md#검수와-게시)에 따라 검수한 MP4 하나를 업로드하고 요청 지면의 영상 미리보기를 확인한다. 최종 이미지·영상의 잘림, 줄바꿈, 표지와 한글을 확인한다. 용량·비율 오류는 해당 채널용 파일을 다시 내보내 해결한다.

   다중 파일 선택 인자의 순서를 실제 사진 순서로 간주하지 않는다. 2026-11-01 4화에서는 `01..04` 일괄 선택 후 실제 첨부가 `04,01,02,03`으로 표시됐다. 순서가 섞이면 아직 제출하지 않은 이번 첨부만 보존·정리하고 한 장의 업로드 완료를 확인한 뒤 다음 장을 추가하는 방법을 쓸 수 있다. 대체텍스트는 **실제 썸네일의 장 번호·이미지 정체성과 연결해** 입력하고, 정렬을 바꿨으면 모든 연결과 저장값을 다시 확인한다. 목록의 위치만으로 화상을 추정하거나 게시 후에 순서를 고치겠다고 제출하지 않는다.
3. 채널별 맞춤 문구 기능이 있으면 각 캡션을 넣는다. 없다면 채널별 작성 화면으로 나누어 각각의 문안을 입력한다. 지원되는 위치에 대체텍스트를 넣고 기능이 없으면 그 한계를 기록한다.
4. 공개 범위, 게시/초안/예약 방식, 선택 계정, 원문 최신성, 검수 상태를 확인한다. 기존 사용자 요청에 맞게 이력을 기록한 뒤 제출한다.
5. 완료 메시지뿐 아니라 콘텐츠 목록과 공개 게시물 페이지를 다시 열어 해당 계정·문구·카드 수·순서가 맞는지 확인한다. 두 채널의 공개 URL/게시물 ID와 확인 시각을 각각 기록한다. 예약 글은 예약 목록에서 확인하고 공개 게시라고 보고하지 않는다.

### Facebook 링크 게시 한도로 막힌 경우

Meta Business Suite의 게시 버튼 비활성·무응답을 사진이나 대체텍스트 오류로 단정하지 않는다. 작성 화면의 안내를 읽고, 아직 제출 전이라면 같은 페이지의 Facebook 기본 작성 화면에서도 제한 안내를 확인한다. 2026-10-22 실행에서는 기본 작성 화면에 ‘이번 달 링크 게시물 2개 사용’과 유료 구독 안내가 표시됐다. 이 관찰만으로 Business Suite의 모든 비활성 상태의 원인이 링크 한도라고 확정하거나 모든 계정의 고정 한도로 일반화하지 않는다.

링크 한도가 확인되면 유료 구독 없이 **Facebook 캡션의 클릭 URL을 `포항TP 홈페이지 → 알림마당 → 사업공고 → 해당 사업명 검색`으로 바꾸는 문안 대안**을 검토할 수 있다. 이미지에 넣은 상세 공고의 실제 QR과 검증된 사업정보는 유지하고, 수정 문안·미리보기·QR 및 실제 차단 해제 여부를 확인한다. `produced`를 이미 기록했다면 원본 패키지를 보존한 별도 사본과 새 manifest를 만들고 [미게시 패키지 문안 수정](notice-tracking.md#미게시-패키지의-플랫폼-문안-수정)의 `revise-produced`로 연결한다.

이번 실행에서 확인된 Facebook 진행 경로는 **Business Suite의 새 Facebook 단독 작성 화면 → 원문 URL을 뺀 검수된 캡션을 클립보드·Ctrl+V로 입력(신청 이메일 유지) → 카드 6장·대체텍스트 6개 → 요청하지 않은 스토리 공유 끄기 → 실제 문안·계정·게시 버튼 활성화 확인**이었다. 이 경로로 게시와 공개 게시물 확인까지 완료했지만, URL 제거만의 효과를 독립적으로 확인한 것은 아니다. 앞선 화면에서 같은 제한 안내가 남았다는 관찰도 보존한다. Instagram도 Business Suite의 Instagram 단독 작성 화면에서 클립보드 입력·카드·대체텍스트 등록으로 게시했다. 두 채널 모두 공개 게시물의 6장 순서·대체텍스트를 확인했고, 게시된 마지막 카드의 화면 캡처에서 QR이 실제 상세 공고 주소로 해독됐다.

문안 교체 후에는 작성란의 실제 값과 다음 화면을 다시 읽는다. 이번 실행에서는 `fill('')`가 기존 문구를 선택하기만 하고 React 편집기의 값은 남긴 현상이 관찰됐다. 그런 경우 지원되는 UI 조작으로 작성란 전체 선택 → Backspace로 삭제 → 준비된 문안 붙여넣기를 수행하고 실제 내용이 바뀌었는지 확인한다. 도구 호출이 성공했다는 사실만으로 URL 제거·한도 해제를 기록하지 않는다.

이 변경은 제출 전에만 진행한다. 이미 제출했거나 `submitting`·`unknown`이면 기존 시도의 실제 결과를 먼저 확인한다. 결과가 불명확한 상태에서 새 패키지나 작성 화면으로 다시 제출하지 않는다. 한 채널이라도 게시·예약됐다면 이 패키지 교체 경로를 사용하지 않는다.

2026-10-28 공고 8158 실행에서는 링크를 추가한 뒤 게시 버튼이 비활성화되고 `링크 0개 남음`이 표시됐다. URL 제거·채널 전환만으로는 회복되지 않았다. **아직 제출하지 않은 작성 화면**의 내용과 증거를 보존한 뒤 그 실행에서 만든 미저장 변경만 삭제하고 새 작성 화면에 같은 포스터·검수된 링크 없는 문안을 입력하자 두 채널 게시가 가능했다. QR과 이미지에 인쇄된 접수 도메인, 캡션의 공식 시스템명·홈페이지 경로·문의는 유지했다. 이는 당시 복구 사례이며 링크 한도가 유일한 원인이었다거나 새 작성 화면이 항상 해결책이라고 단정하지 않는다. 기존 게시·예약·초안은 지우지 않으며, 제출 여부가 불명확하면 이 경로를 쓰지 않는다.

같은 실행의 한국어 작성란에서는 붙여넣기 앞뒤에 잔여 글자가 생기고 `fill()` 뒤 보이는 내용과 채널 전환 후 저장된 내용이 달라지는 현상도 관찰됐다. 편집기에 포커스 → Escape → 전체 선택 → 삭제 후 **실제로 빈 작성란인지 확인**하고 확정 문안을 붙여넣는다. 채널 전환 후 다시 읽어 원문과 대조하고 UI가 만드는 빈 줄 차이만 허용한다. 화면의 문자 수정만 보고 저장 완료로 판단하지 않는다.

## 실패·중단 후 이어가기

### 사용자가 확정한 이미지로 기존 게시물 교체

사용자가 완성 이미지를 보고 기존 게시물 교체를 요청하면 그 요청을 해당 공고·계정·이미지 해시에 연결하고 진행한다. 같은 승인을 다시 묻지 않는다. Facebook처럼 기존 글의 사진 편집이 가능한 경우 주소·댓글을 보존해 첨부 사진만 교체하고 새 대체텍스트·원본 비율·공개 범위·AI 표시를 확인한다. 실제 편집 저장은 신규 게시 성공 이벤트로 덮어쓰지 않고 패키지의 `replacement-operation.json`과 `publication-results.json`에 기존 attempt/post ID·새 photo ID·이미지 manifest 해시·확인 시각·공개 화면을 연결한다.

사진 교체가 불가능해 삭제·재게시가 필요한 경우, 먼저 새 글의 이미지·문안·대체텍스트와 최신 접수기간을 준비하고 원글을 정확한 ID로 확인한다. 사용자 요청 범위 안에서 지원되는 삭제/보관 절차를 사용한다. 복구 불가능한 영구 삭제 등 실제 화면과 적용되는 실행 정책이 추가 확인을 요구하면 해당 동작만 사용자에게 요청한다. 삭제 성공 메시지와 원래 공개 주소·목록을 대조해 제거를 확인한다. 단순히 조회되지 않는다는 이유로 삭제 성공을 추정하지 않는다.

원글이 제거된 재게시만 `publication_history.py record --status submitting --replacement-evidence <JSON>`을 사용한다. JSON에는 `previous_attempt_id`, `previous_post_id`, 실제 `user_request_evidence`, `old_removed_verified=true`, 시간대 있는 `removed_at`, 절대경로 `deletion_evidence_path`·그 파일의 SHA-256 `deletion_evidence_sha256`, 새 `replacement_manifest_sha256`을 둔다. 기존 성공 이벤트는 보존하고 새 attempt의 `replacement`로 연결한다. 같은 공고·계정의 다른 성공·불명 시도가 있거나 원글/증거/패키지가 맞지 않으면 차단한다. 새 시도의 결과가 불명확하면 다시 제출하지 않고 원래 시도부터 확인한다. 원글 삭제만으로 장부를 `failed`로 바꾸거나 다른 source key로 중복 차단을 우회하지 않는다.

Instagram 성공, Facebook 실패라면 Instagram 결과를 유지하고 Facebook만 처리한다. 삭제에 성공했으나 교체 제출이 확정 실패했다면 같은 삭제 증거와 원글 ID를 다시 연결해 해당 채널을 재시도한다. 원격 결과가 불명확하면 원래 시도를 먼저 조정한다. 과거 확인 대기 기록은 증빙으로 보존하며 현재 상태는 채널별 장부에서 다시 읽는다. 두 채널 공통 게시 버튼에서 일부만 반영됐을 때도 각 채널을 따로 확인한다. 성공 글을 임의 삭제·재게시하여 맞추지 않는다.

장부에는 `published`가 있지만 실제 글이 삭제됐거나 계정에서 찾을 수 없으면 불일치를 보고하고 사용자 의도를 확인한다. “찾을 수 없음”만으로 실패 처리하여 재게시하지 않는다. 로그인·권한 문제는 인증·권한이 해소된 후 해당 단계부터 재개한다.

최종 응답에는 두 채널의 `게시 완료 / 예약 완료 / 미게시 / 확인 필요`와 실제 링크를 적는다. 게시물이 생성됐지만 외부에서 공개 노출을 확인하지 못했다면 그 범위를 구분한다. 로컬 카드 제작, 업로드, 게시 요청 성공, 실제 공개 확인을 하나의 “완료”로 합치지 않는다.
